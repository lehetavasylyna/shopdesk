# The Shelf — матеріал для презентації

Система обліку замовлень для невеликого магазину господарчих товарів.  
Тема практики: розроблення системи керування замовленнями для малого онлайн-магазину.  
Період: 14.09.2026 – 02.10.2026.

Інтерфейс англійською. Підпис у шапці — **order desk**. Дані прикладів теж англійською: Helen Parker, Uzhhorod, Desk lamp.

Кожен розділ нижче — один слайд. Маркований список можна ставити на слайд. Абзац «Що сказати» — текст для усного пояснення.

---

## 1. Задача

- Магазин веде покупців, товари і замовлення.
- Замовлення створюють, підтверджують, відправляють, завершують або скасують.
- Залишок змінюється в ту саму мить, коли замовлення збережено.
- Ціна в чеку фіксується на момент замовлення.
- Стіл замовлень закритий входом працівника.

**Що сказати.** Це не таблиця з готовими цифрами. Працівник заводить замовлення в програмі, і кожне збереження одразу змінює склад. Старий чек не перераховується, якщо товар потім подорожчає.

---

## 2. Три речі, які папір не закриває разом

1. Хто купив, що саме і на яку суму.
2. Останню річ не можна продати двічі: залишок списується при збереженні.
3. Замовлення йде далі по статусах, і видно, коли статус змінився і хто це зробив.

**Що сказати.** Список покупців без складу — це записник. Склад без статусів — це лише залишок. Тут обидва боки в одному збереженні.

---

## 3. Як влаштована програма

```
браузер (React, порт 5173)
        |  fetch /api/...   JSON
        v
Express (порт 5000)
        |  better-sqlite3
        v
shop.db (один файл SQLite)
```

- Сервер нічого не малює. Він перевіряє сесію, читає або змінює базу і повертає JSON.
- Клієнт не рахує суму чека і не вирішує, чи можна змінити статус.
- Порушене правило — відповідь 400 і звичайне речення в полі `error`. Браузер показує його зверху сторінки.
- Невідома адреса — 404. Несподіваний збій — 500 з текстом «Something went wrong», без деталей бази.

**Що сказати.** Дві частини запускаються окремо. Браузер ходить лише на `/api`. Vite пересилає ці запити на порт 5000.

## 4. Технології

| Частина | Чим зроблено | Навіщо |

| Адреси в браузері | React Router 6 | Список, нове замовлення, чек, товари, покупці, зведення |

**Що сказати.** Програма відкривається на ноутбуці. MySQL для такого магазину зайвий: уся база — один файл поруч із кодом.

## 6. База: сім таблиць

| Таблиця | Що зберігає |
| --- | --- |
| `customers` | ім’я, телефон, місто, адреса |
| `products` | назва, категорія, ціна, залишок |
| `orders` | покупець, статус, коментар, сума, дата, доставка |
| `order_items` | товар, кількість, ціна на момент замовлення |
| `order_events` | кожна зміна статусу: коли і хто |
| `staff` | обліковий запис: ім’я, логін, хеш пароля |
| `sessions` | токен чинної сесії |

```
customers 1 —— * orders 1 —— * order_items * —— 1 products
                      |
                      * order_events

staff 1 —— * sessions
```

**Що сказати.** Покупець може існувати без замовлень. Товар теж. Замовлення без покупця і рядок без товару база не прийме: це зовнішні ключі. Позиції винесені окремо, бо той самий товар буває в різних чеках.

---

## 7. Що тримає схема

- Ціна товару і ціна в рядку чека більші за нуль.
- Залишок не від’ємний. Сума замовлення теж.
- Статус лише один із п’яти: `new`, `confirmed`, `shipped`, `completed`, `cancelled`.
- Видалення замовлення забирає його рядки і історію (`ON DELETE CASCADE`).
- Товар, який уже стоїть у чеку, видалити не можна: на `product_id` каскаду немає.
- Індекси: статус замовлення, покупець, рядки одного чека.

У SQLite зовнішні ключі самі не працюють. `openDb` у `src/db.js` вмикає їх на кожному з’єднанні:

```sql
PRAGMA foreign_keys = ON;
```

Поля доставки і ім’я працівника в історії з’явились пізніше. Якщо файл бази вже був без них, `migrate` додає колонки через `ALTER TABLE`.

**Що сказати.** Без `PRAGMA foreign_keys = ON` товар із чека можна було б стерти, і рядок лишився б без товару. Це окремо перевірено тестом.

---

## 8. Правила покупця і товару

Покупець:

- ім’я після обрізання пробілів — щонайменше 2 символи;
- у телефоні щонайменше 10 цифр; пробіли, дужки і дефіси не рахуються;
- порожнє місто стає `Uzhhorod`.

Товар:

- назва від 2 символів;
- категорія лише зі списку: Kitchen, Tableware, Textiles, Household;
- ціна — ціле число більше нуля;
- залишок — ціле число, нуль можна, мінус не можна;
- якщо товар уже в замовленні, видалення відмовляє реченням «This product is already in an order, so it cannot be deleted».

Правка картки товару змінює поточну ціну і залишок. Старі чеки від цього не змінюються: у `order_items.price` лежить копія.

**Що сказати.** Категорія — не вільний текст. Список тримає сервер, форма показує його випадаючим списком.

---

## 9. Нове замовлення і склад

`placeOrder` дивиться на `customer_id`.

- число — наявний покупець;
- `"new"` — спочатку створюється покупець, потім замовлення;
- порожньо — відмова.

Якщо замовлення не збереглось через залишок, новий покупець усе одно лишається. Телефон не треба набирати вдруге.

Далі в одній транзакції:

1. Порожні рядки відкидаються. Однаковий товар зводиться в одну кількість.
2. Має лишитись хоча б один товар. Кількість більша за нуль.
3. Доставка: `pickup` (доплата 0) або `courier` (доплата 80 грн).
4. Для кожного товару залишок зменшується запитом `UPDATE ... SET stock = stock - ? WHERE id = ? AND stock >= ?`.
5. У рядок чека пишеться поточна ціна. Сума з браузера не читається.
6. Замовлення отримує статус `new` і перший запис в історії.

Якщо другий товар не вміщається, відкочується все: і вже зменшений залишок першого, і саме замовлення.

**Що сказати.** Умова `stock >= ?` у самому запиті не дає двом збереженням списати один і той самий залишок. Якщо оновився не рівно один рядок, транзакція падає.

## 10. Статуси

| Зараз | Можна перейти в |
| --- | --- |
| `new` | `confirmed`, `cancelled` |
| `confirmed` | `shipped`, `cancelled` |
| `shipped` | `completed` |
| `completed` | нікуди |
| `cancelled` | нікуди |

- З `new` не можна стрибнути в `completed`.
- Той самий статус вдруге не ставиться.
- Скасувати можна лише до відправки. Тоді кількість кожного рядка повертається на склад, теж в одній транзакції.
- З `shipped` і `completed` назад дороги немає. Відправлене залишок не повертає, бо такий перехід просто не дозволений.
- Форма на екрані показує лише ті переходи, які сервер поклав у `nextStatuses`. Якщо масив порожній, форми немає.

Ім’я з сесії пишеться в `order_events.staff_name`. Для облікового запису це `Shop desk`.

**Що сказати.** Склад змінюється двічі за життя замовлення: при створенні і при скасуванні. Підтвердження і відправка склад не чіпають.

---

## 11. Ціна в чеку і доставка

- Поле `orders.total` зберігається, а не рахується щоразу з поточного прайса.
- У рядку чека своя ціна. Чайник завтра подорожчає — старе замовлення лишається зі старою ціною.
- Самовивіз нічого не додає. Кур’єр додає 80 грн у поле `delivery_fee`.
- Ця доплата лишається в чеку, навіть якщо пізніше змінити ціну товару.

Поки статус `new` або `confirmed`, рядки, коментар і доставку можна змінити. Правка — одна транзакція:

1. Стара кількість повертається на склад.
2. Старі рядки видаляються.
3. Нові рядки списуються.
4. Якщо новий набір не вміщається, уся зміна відкочується. Чек лишається як був.
5. Товар, який уже був у цьому замовленні, тримає стару ціну. Новий товар бере сьогоднішню.

Після `shipped` сервер відповідає: замовлення вже в дорозі, рядки не змінюються.

**Що сказати.** Це головне правило чека. Ціна — знімок на момент замовлення, доставка — окрема фіксована сума, невдала правка не лишає склад наполовину зміненим.

---

## 12. Список, пошук, «зависле» замовлення

Список читається з бази. Фільтр статусу — умова SQL.

Далі в JavaScript, бо список короткий:

- пошук за ім’ям, телефоном, містом, коментарем і номером замовлення;
- діапазон дат `from` і `to`;
- сортування: спочатку нові, спочатку старі, більша сума, менша сума.

Пошук навмисно не через `lower()` у SQLite: ця функція не з усіма літерами надійна. «helen» знаходить Helen Parker.

Під таблицею — кількість знайдених рядків і сума саме цих рядків.

Якщо статус досі `new` або `confirmed`, а з дати створення минуло більше двох днів, у відповіді `waiting` дорівнює 1. На екрані дата такого рядка позначена. Поріг рахується від створення, не від останньої зміни статусу. Відправлене, виконане і скасоване так не позначаються.

**Що сказати.** На захисті можна набрати `helen` і показати, що пошук бере ім’я, а не лише номер. Дати прикладу всередині вересня, тож замовлення Helen у статусі `new` уже позначене як таке, що висить.

## 13. Зведення

`summary` для кожного з п’яти статусів рахує кількість замовлень і суму `total`. Усі п’ять рядків є завжди, навіть якщо кількість нуль.

Скасовані входять у свій рядок. На сторінці є речення: ці гроші пораховані, але це не виручка.

Окремо — товари, у яких `stock <= 3`. Той самий поріг фарбує клітинку залишку жовтим на сторінці товарів.

**Що сказати.** У короткому прикладі лампа лишається на трьох штуках і потрапляє в цей список. У повному наборі на малому залишку лишається мітла.

## 14. Вхід

Один обліковий запис, створюється сам, якщо таблиця `staff` порожня.

- ім’я: Shop desk
- логін: `desk`
- пароль: `shelf2026`

Пароль у базі не лежить. `hashPassword` бере випадкову сіль на 16 байт і рахує `scrypt`. У колонці рядок `сіль:хеш`. Під час входу байти порівнюються через `timingSafeEqual`.

Кука називається `shelf`. Вона `HttpOnly`, `SameSite=Lax`, `Path=/`. Терміну дії немає: сесія живе, поки її не видалять виходом.

- без куки API відповідає 401 і текстом `Sign in first`;
- невірний пароль — 400, бо це помилка правил, не відсутність сесії;
- вихід ставить `Max-Age=0` і видаляє рядок із `sessions`.

**Що сказати.** Сторінка скриптом куку не читає. Без сесії меню немає, на екрані лише форма входу.

Рядків товару спочатку чотири. Кнопка `another line` додає ще один у стані React, без запиту на сервер.

**Що сказати.** Вигляд зібраний в одному `styles.css`, без бібліотеки компонентів. Темна смуга зверху, білий аркуш до 1080px, статус — кольорове слово.

## 16. Що відбувається в типових діях

Це зручно проговорити під час показу, крок за кроком.

1. **Увійти.** Сервер звіряє хеш, пише випадковий токен у `sessions` і ставить куку.
2. **Додати товар.** Назва, категорія, ціна, залишок. Сервер перевіряє поля і вставляє рядок.
3. **Нове замовлення.** Рядки зводяться, у транзакції зменшується залишок, пишуться чек, ціна на зараз і подія `new`.
4. **Новий покупець із тієї самої форми.** Спочатку рядок у `customers`. Якщо залишку не вистачило, покупець уже є, замовлення немає.
5. **Підтвердити.** Статус `confirmed`, у історію додається ім’я Shop desk. Склад не змінюється.
6. **Відправити.** З `confirmed` у `shipped`. Рядки і скасування закриваються.
7. **Завершити.** З `shipped` у `completed`. Форма статусу зникає.
8. **Скасувати.** Лише з `new` або `confirmed`. Кількості повертаються на склад.
9. **Змінити рядки відкритого чека.** Старий залишок повертається, нові рядки списуються. Старий товар тримає стару ціну.
10. **Змінити ціну в картці товару.** Міняється лише прайс. Уже записані чеки лишаються.
11. **Видалити товар із чека.** База відмовляє, на екрані звичайне речення.

## 17. Сценарій показу

Перед захистом у двох терміналах:

```bash
npm install
npm start
```

```bash
cd client
npm install
npm run dev
```

Відкрити http://127.0.0.1:5173  
Логін `desk`, пароль `shelf2026`.

Короткий приклад збирається сам, якщо `shop.db` порожній: 12 товарів, 4 покупці, 4 замовлення.

| Покупець | Місто | Що в чеку | Статус | Сума |
| --- | --- | --- | --- | --- |
| Helen Parker | Uzhhorod | чайник і дві упаковки губок, «call back after 6 pm», 21.09.2026 | new | 980 |
| Mark Ellis | Mukachevo | праска і вішаки, 23.09.2026 | confirmed | 1 370 |
| Irene Berg | Uzhhorod | ковдра і два комплекти рушників, 28.09.2026 | shipped | 1 630 |
| Thomas Wood | Chop | чашки і два набори контейнерів, 01.10.2026 | completed | 780 |

Самовивіз у цьому прикладі скрізь. Лампа починає з 3 штук і в замовлення не входить, тому клітинка жовта. Чайник починає з 8, одну штуку забирає Helen, у базі його 7.

Порядок на екрані:

1. Увійти. Показати, що без пароля меню немає.
2. Orders. Набрати `helen`. Показати позначену дату: замовлення висить у `new` довше двох днів.
3. Відкрити чек Helen. Показати ціну рядка, коментар і історію зі статусом `new`.
4. Перевести в `confirmed`. У історії з’являється ім’я Shop desk. Залишок чайника не змінюється.
5. New order. Обрати товар, якого мало, і показати відмову «Not enough…». Залишок на сторінці товарів той самий.
6. Products. Показати жовту лампу. Спробувати видалити чайник: він уже в чеку, сервер відмовляє.
7. Customers. Відкрити Helen і показати її замовлення.
8. Summary. П’ять статусів і лампа в малому залишку.

Повніший магазин для показу сторінки покупця з двома чеками і кур’єром:

```bash
npm run mock
```

Це 20 товарів, 12 покупців і 14 замовлень з 21.09.2026 по 02.10.2026. Є кур’єр, скасування, два замовлення Helen. Скрипт замінює рядки в тому самому `shop.db` і не чіпає обліковий запис `desk`. Після нього краще перезапустити `npm start`.

Щоб повернути короткий приклад: зупинити сервер, видалити `shop.db`, знову `npm start`.

## 18. Тести

```bash
npm test
```

Файл один: `test/shop.test.js`. Кожен тест створює тимчасову теку і свій `shop.db`. Робочий файл тести не відкривають.

Що закрито перевірками:

- сума і списання залишку, злиття двох рядків одного товару;
- відкат, коли другий рядок не вміщається;
- стара ціна в чеку після зміни прайса;
- повернення залишку при скасуванні і заборона скасувати відправлене;
- шлях `new → confirmed → shipped → completed` і заборона стрибка через статус;
- правка відкритого чека і відкат невдалої правки;
- кур’єр додає 80, самовивіз забирає ці 80;
- пошук, дати, сортування, поріг «два дні»;
- товар із чека не видаляється;
- зведення, малий залишок, замовлення покупця;
- вхід: без куки 401, невірний пароль 400, після виходу стара кука знову 401;
- пароль у базі — сіль і хеш, не текст `shelf2026`;
- сама SQLite не приймає нульову ціну, від’ємний залишок і статус поза списком.

**Що сказати.** Тести перевіряють правила, а не вигляд кнопок. Вони ходять і в функції, і звичайним `fetch` до API на тимчасовому порту.

## 19. Обмеження

- Один обліковий запис. Реєстрації інших працівників немає.
- Сесія без терміну дії. Вийти можна кнопкою Sign out.
- Немає оплати, друку чека, ролей і кількох магазинів.
- Сервер — один процес на ноутбуці. Кілька людей одночасно ця збірка не розрахована обслуговувати.
- Пошук і сортування списку йдуть у пам’яті після читання рядків. Для короткого списку цього досить.
- Зібраний клієнт (`npm run build` у теці `client`) сам API не містить. Для перегляду достатньо `npm start` і `npm run dev`.

**Що сказати.** Обмеження свідомі: обсяг практики — облік одного столу, не мережа магазинів.

## 20. Чим закінчити

Програма придатна як облік замовлень малого магазину.

- Замовлення створюють і ведуть у системі, а не вписують у готову таблицю.
- Склад і чек змінюються разом: транзакція або проходить цілком, або відкочується.
- Ціна в рядку — знімок. Статус іде лише дозволеним порядком. Скасування до відправки повертає товар.
- Вхід закриває стіл. Історія показує, хто змінив статус.
- Поведінку перевірено тестами на окремій базі.

**Що сказати.** Найзмістовніша частина — правила в `src/orders.js`, не форми. Форма може надіслати будь-який статус. Сервер пропустить лише той, який дозволений з поточного.
